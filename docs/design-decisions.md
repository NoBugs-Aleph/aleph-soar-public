# 해결하려는 문제와 설계 의도

## 출발점

민원포털에서 로그인 실패가 발생하고 방화벽·호스트에도 로그가 남더라도,
로그를 모았다는 사실만으로 공격 차단과 정상 사용자 보호를 증명할 수는 없습니다.
NoBugs는 **신호 수신 → 사건 판정 → 대응 → 효과 확인 → 원복**을 하나의 기록으로 연결합니다.

가상 해담시청의 보호 대상은 다음과 같습니다.

| 보호 대상 | 필요한 확인 | 연결 케이스 |
| --- | --- | --- |
| 시민·직원 계정과 세션 | 공격 대상과 정상 사용자를 구분해 접근 제어 | S1·S4 |
| 민원 서비스의 웹 파일 | 변경·접근을 연결하고 정상 기준본으로 복구 | S7 |
| 서비스 접근 경로 | 앱·인증·경계 신호를 결합하고 집행 위치별 효과 확인 | S8·S10 |
| 정상 사용자의 서비스 이용 | 정상 기준선과 공격 중 응답·회복을 비교 | S12 |

이 표는 설계 목적입니다. 민원 데이터 유출 방지나 전 케이스 가용성 개선을
모두 실증했다는 뜻은 아닙니다. [검증 현황](verification.md)과 함께 읽습니다.

## 구성 요소를 나눈 이유

| 선택한 구성 | 맡긴 역할과 이유 | 단독으로 증명하지 못하는 것 |
| --- | --- | --- |
| React·Flask·MySQL | 정상 업무가 있는 서비스와 실제 대응 대상을 제공. 화면·API·저장 상태를 대조 | 보안 제품의 전체 기능이나 운영 환경 안정성 |
| Graylog | 서로 다른 소스의 필드를 정규화하고 시간 창·그룹 조건으로 결합 | 원문이 도착했다는 사실만으로 탐지·조치 성공 |
| Wazuh | 웹 요청만으로 확인하기 어려운 파일 생성·변조·삭제를 관찰하고 복구 경로 제공 | FIM 경보만으로 악성 변경 또는 복구 효과 확정 |
| Suricata | 네트워크 트래픽의 IDS 신호를 관제 근거에 추가 | 경보만으로 실제 차단·서비스 회복 보장 |
| pfSense·OpenVPN | 실습 경계 통제·팀 연결·네트워크 집행 위치 제공 | 규칙 존재만으로 상대 서비스 접근 성공/실패 |
| n8n | 탐지 결과를 대상 API·티켓·효과/원복 절차에 연결 | HTTP 성공 응답만으로 실제 대상 상태·효과 확정 |
| 티켓 저장소·대시보드 | 사건과 조치의 경로·대상·효과·해제·종료를 구분 | 티켓 닫기만으로 차단 해제 |

이는 현재 구성의 역할과 설계 의도를 설명한 것입니다. 대안 제품 간 성능 벤치마크나
특정 도구가 더 우수하다는 비교 실험은 하지 않았습니다.

## 중요한 설계 구분

### 앱 차단과 경계 차단

같은 대상이라도 앱과 방화벽은 다른 집행 위치입니다. 티켓 조치를 경로별로
구분하고, 실제 접근 효과와 각 위치의 해제를 따로 확인합니다.
S1의 앱 차단 성공을 S10 방화벽 집행 성공으로 확대하지 않습니다.

### 사건 상태와 실제 자원 상태

하나의 사건에 여러 조치가 붙을 수 있고 여러 사건이 같은 대상을 사용할 수 있습니다.
티켓 상태만 보고 해제를 허용하지 않도록 활성 조치와 소유권을 별도로 다룹니다.

### 반복 측정과 이전 회차 분리

시간 창·기존 차단·열린 티켓이 다음 실행에 섞이지 않도록 새 실행과 원복 상태를
기록합니다. 기능 수와 로컬 테스트 수 대신 실제 흐름의 검증 범위를 보고합니다.
