# 김명준 · 네트워크 기반 구성 및 통합 검증

**해담시청 보안 관제 팀 프로젝트 / NoBugs / B 담당·조장 / GitHub: myeongjundev**

기록 기준: **2026-11-03** · 공개 요약 작성: **2026-11-04**

## 맡은 범위

pfSense·OpenVPN·DB·Kali 실습 기반과 S8/S10 시험 입력·네트워크 효과 확인을 맡고,
포털·관제·티켓 담당자와 입력 조건, 확인 순서, 원복 상태를 맞추는 통합 조율을 진행했습니다.
초기 React·Flask 포털 구현에도 Codex를 활용했습니다.
이 문서는 해당 담당 범위의 기여를 설명하며, 팀 전체 기능을 개인 단독 구현으로 주장하지 않습니다.

## 1. 분산 환경의 연결과 규칙 확인

4대 PC로 나뉜 실습 환경에서 기존 유선망과 팀 VPN을 활용하는 구성을 준비했습니다.
B 담당의 DB 기반을 구성하고 VPN 접속·허용 규칙·기본 차단을 구분해 점검했습니다.

10/20 기록에서는 Ping 요청이 대상에 도착했는데 응답을 받지 못하는 상황을 패킷 캡처로 좁혔습니다.
허용 규칙이 Echo request 대신 Echo reply로 설정된 것을 확인하고 수정한 뒤 Ping 4/4 성공을 기록했습니다.
이는 해당 경로의 재확인 결과이며, 그날 모든 팀 PC와 서비스의 통합 연결이 완료됐다는 뜻은 아닙니다.

TCP 접속 실패 관찰과 다른 프로토콜의 방화벽 차단 로그도 구분했습니다.
연결 실패라는 결과만으로 특정 방화벽 규칙이 원인이라고 단정하지 않았습니다.

## 2. 입력·탐지·실제 효과를 나눠 확인

S8/S10에서 출발지와 시간 구간을 나눠 시험 입력을 수행하고,
A의 포털 원본, D의 수신·상관탐지·대응, C의 저장·티켓 기록을 연결해 확인하는 역할을 맡았습니다.

11/3 S10 PF 첫 인수는 자동 해제가 실패해 B 담당에서 수동 정리했습니다.
도구 보완 뒤 재인수와 실제 탐지 회차를 분리했고,
실제 회차에서는 PF 해제 후 포털 403, 포털 해제 후 200 복귀를 순서대로 대조했습니다.
B의 입력·접근 결과와 다른 담당자의 내부 상태 보고를 합쳐 판단한 팀 검증입니다.

11/2 S7에서는 웹 접근 성공과 실제 티켓 저장, 실제 자동 대응 실행을 각각 구분했습니다.
팀원에게 전달받은 저장·AR 실행 여부를 B가 그 장비에서 직접 조회한 결과로 바꾸어 쓰지 않았습니다.

## 네트워크 엔지니어 지원 경험으로 연결되는 점

- **접근 경로 확인:** VPN 접속 표시와 실제 서비스 도달성·허용/거부 결과를 나눠 확인했습니다.
- **문제 범위 축소:** 패킷 도착·규칙 조건·서버 원본·응답을 비교해 실패 지점을 좁혔습니다.
- **집행 위치 구분:** 네트워크 경계와 앱 차단을 나누고 각각의 해제·접근 복귀를 확인했습니다.
- **검증 기록 관리:** 실패·수동 복구·재시험을 별도 결과로 남기고 팀원 보고의 출처를 구분했습니다.

공식 기업 운영이나 실제 침해 사고 대응 경험으로 표현하지 않습니다.
위 내용은 팀의 교육용 환경에서 확인한 역할과 결과입니다.
