# 문제를 확인하고 개선한 과정

아래는 실제 개발·실습 기록을 바탕으로 다시 작성한 공개 요약입니다.
증상, 원인 확인 수준, 수정과 검증 범위를 구분합니다.

## 1. 차단 API가 본문 오류로 거부됨

- **증상:** n8n에서 실제 차단을 요청했지만 포털이 JSON 객체 오류로 거부했습니다.
- **원인 확인:** 초기에는 JSON 문자열 직렬화를 의심했습니다. 이후 포털의 요청 캡처에서
  본문 길이 0·Content-Type 없음이 확인돼 실제 본문 미전송으로 범위를 좁혔습니다.
- **조치:** 실행 HTTP 노드의 본문 전송을 명시적으로 켜고 JSON 필드 방식과 게시본을 대조했습니다.
- **재검증:** 10/27 차단 요청의 본문 수신·대상 반영 보고와 B의 실제 접근 거부를 대조했습니다.
  다음 날 S1 자동 차단 시험에도 대응 API를 사용했습니다.
- **배운 점:** 생성 파일·화면 설정·실제 게시본·서버가 받은 요청을 각각 확인해야 합니다.
  응답 코드만으로 본문이나 인증 문제가 무엇인지 단정하지 않습니다.

## 2. 서비스는 실행 중인데 로그가 도착하지 않음

- **증상:** pfSense Syslog 송신 설정이 있어도 Graylog 수신이 멈췄습니다.
- **원인 확인:** B 송신 설정과 D Docker UDP 전달 상태를 분리해서 확인했습니다.
  담당 기록상 수신측 전달 경로가 멈춰 있었고 D가 컨테이너를 재시작한 뒤 복구됐습니다.
- **재검증:** 합의된 준비 표본 1건을 보내 원문·정규화 수신을 대조했습니다.
- **한계:** 작은 표본의 도착이 장시간·고부하 무손실을 보장하지는 않습니다.
- **배운 점:** 프로세스 기동과 실제 입력 수신을 별도 항목으로 점검합니다.

## 3. 늦게 도착한 효과 보고와 닫힌 티켓

- **증상:** 격리 재현에서 이전 회차 효과가 새 차단을 검증 완료로 만들거나,
  티켓을 닫으면 남은 활성 차단이 조회에서 보이지 않는 문제가 나타났습니다.
- **조치:** 활성 조치·효과 시각·닫기 조건·대상 조회를 보완하고 회차 분리 정책을 맞췄습니다.
- **재검증:** 이전 효과 거부, 새 조치의 검증 상태 유지, 해제 전 닫기 거부,
  기존 닫힌 데이터의 활성 조치 조회를 격리 검사했습니다.
- **한계:** 격리 회귀 검사를 서로 다른 실제 사건의 모든 동시·지연 조합을 검증한 것으로 세지 않습니다.
- **배운 점:** 사건의 화면 상태와 실제 자원 소유권을 같은 것으로 취급하면 안 됩니다.

## 4. NTP 상태는 정상인데 시각이 과거에 머무름

- **증상:** 10/29 VM 재개 뒤 NTP 표시가 정상이어도 장비 시각이 전날에 머문 상태를 발견했습니다.
- **조치·확인:** 실제 시간 응답을 별도로 비교하고 기존 시간 서비스를 재시작해 장비 추종을 확인했습니다.
  Windows 잔여 오차는 별도 관리자 동기화·재측정 과제로 남겼습니다.
- **배운 점:** 동기화 표시와 실제 시각 차이를 분리해야 탐지·대응 지연을 해석할 수 있습니다.
  이번 시각 복구 자체를 공격 시험의 성과로 기록하지 않습니다.

## 기록 원칙

실패 기록과 첫 관찰을 보존하고, 원인 추정과 확인된 원인을 나눕니다.
도구 테스트·담당 보고·실제 장비 결과는 같은 단계의 성공 수로 합산하지 않습니다.
원본은 비공개 개발 저장소의 10/27~10/28 B 일지와 10/28 S1 현장표에서 평가 권한으로 확인할 수 있습니다.
4번(10/29 시각 문제)의 B 일지는 아직 저장소에 올리지 않았습니다.
