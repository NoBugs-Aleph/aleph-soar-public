## 프로젝트 소개

가상 해담시청 민원포털의 앱·인증·호스트·네트워크 로그를 수집하고, 서로 연결되는 신호를 판정해 대응합니다.
대응 API의 성공 응답과 실제 차단 효과를 구분하고, 정상 사용자의 접근과 해제 후 복귀를 함께 확인합니다.

시민은 민원 작성·제출·조회, 담당자는 배정된 민원 처리·답변, 관리자는 계정·이용 상태 관리를 수행하는 구성입니다.
이 업무가 보안 검증의 보호 대상이며, 모든 사용자 동선을 공격 중 동시에 검증한 것은 아닙니다.
실제 공공기관의 서비스·데이터를 사용하는 프로젝트가 아니며, 시험은 팀 실습 환경에서 수행했습니다.

이 저장소에는 **검토한 공개 문서만** 있습니다. 실행 소스·배포 환경·원문 로그·현장 캡처·시연 영상은 포함하지 않습니다.
개인 방어전과 NetProof 프리미엄 실습은 이 프로젝트의 성과에 포함하지 않습니다.

## 구성과 검증 흐름

역할별 4대 PC에 포털·DB·네트워크·관제 구성요소를 나누고 팀 VPN으로 연결하는 실습 구성입니다.

```mermaid
flowchart LR
    INPUT[합의된 시험 입력] --> PORTAL[React / Flask 민원포털]
    PORTAL --> DB[(MySQL)]
    INPUT --> NETWORK[pfSense / Suricata]
    PORTAL --> GRAYLOG[Graylog 수집·상관탐지]
    NETWORK --> GRAYLOG
    WAZUH[Wazuh 파일 무결성 감시] --> GRAYLOG
    GRAYLOG --> N8N[n8n 대응 흐름]
    N8N --> ACTION[포털·경계 차단 / 계정 잠금 / 파일 복구]
    N8N --> TICKET[티켓 저장소·보안 대시보드]
    ACTION --> VERIFY[공격 효과·정상 사용자·원복 확인]
```

그림은 전체 설계이며, 파일 복구 등 미검증 경로도 포함합니다.
[구성과 검증 흐름](docs/architecture.md)과 [케이스별 검증 현황](docs/verification.md)을 함께 확인해 주세요.

## 대표 검증: 차단 요청과 실제 효과를 구분하기

**S8:** 첫 입력에서는 웹훅 미등록으로 대응 호출이 실패했습니다.
담당자가 등록 상태를 복구한 뒤 새 회차에서 공격 출발지의 403과 정상 출발지의 200을 대조했고,
해제 후 접근 200·잔여 차단 없음·티켓 종료를 확인했습니다.

**S10:** PF 단독 첫 인수에서는 자동 해제가 실패해 B 담당자가 수동 정리했습니다.
도구 보완 뒤 별도 재인수에서 차단·해제·잔여 없음이 확인됐습니다.
이후 실제 상관탐지 회차에서는 PF를 먼저 해제해 포털의 403을 확인하고, 포털도 해제해 양쪽 접근 복귀를 대조했습니다.

[문제 → 보완 → 재시험 해설](docs/integration-walkthrough.md)에서 실패 회차·재시험·남은 한계를 확인할 수 있습니다.
